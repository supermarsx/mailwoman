# Composition formats and local drafts

Plain-text composition creates a `text/plain` MIME body. Literal angle brackets, ampersands and line breaks remain text; switching to rich text creates HTML through the editor schema. Plain-text and armored cryptographic messages do not receive an open-tracking image. Cc and Bcc recipients enter the submission envelope, while the transmitted message omits Bcc headers.

Local unsent drafts are scoped to the authenticated account. They retain the selected identity, body format, inserted-signature identifiers, recipients, threading and uploaded attachment references. Resuming and sending removes that account's original draft. Account changes invalidate pending autosaves, uploads, previews and pre-dispatch tracking work. Already accepted upstream submissions cannot be recalled by changing the current account.

Legacy draft rows without an account identifier are not assigned to whichever user next signs in. Local drafts are plaintext browser storage, cleared on logout; they are not a cross-device server draft synchronization feature. Quoted decrypted content is never autosaved. Stored upload references may expire; resuming does not grant access to another account's blob.

A named signature selected for a native identity resolves the account-owned template at Identity/get time, including edits and removal. Templates can contain sanitized HTML and an independent plain-text alternative. Legacy `body` content remains plain text. Rich composition uses the HTML version, while plain composition uses the text version. Editing the plain alternative preserves it across later rich edits. The dedicated editor also permits explicit HTML-source editing; source is never inserted directly into the page. HTML is limited to 32 KiB and each plain-text field to 64 KiB.

HTML passes the shared sanitizer on save and again during native identity publication. Scripts, event handlers and remote image sources are removed. Existing provider HTML/text signatures and Sent-folder metadata survive profile edits. The signature API checks the optional captured account header; the web client also fences account changes during asynchronous authentication work.

This format checkpoint does not provide owned signature image attachments, mode-specific defaults and placement, a layout maker, domain disclaimers or signature insertion before cryptographic signing. Existing default/rule metadata is preserved; selecting a named template for the identity is the supported application path. Proxy identity-profile persistence remains separate from the native integration described here.
