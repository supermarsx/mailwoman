# Controlled SQLite page-cache target

`database.pool.sqlitePageCacheMiB` defaults to `null`. This leaves SQLx/SQLCipher cache configuration unchanged: no new `PRAGMA cache_size` is supplied. The bundled provider has a compiled negative cache-size default of 2000 KiB, but a database/header or driver configuration can differ; the observed PRAGMA is authoritative. This feature does not change any encryption, MAC, key order, WAL, synchronization or durability setting.

A custom integer from 16 through 1024 specifies an aggregate **soft target for the MAIN database across the planned maximum foreground pool connections**. Each foreground connection receives `floor(MiB * 1024 / plannedMaximum)` KiB, through a session-only negative `cache_size`. This is a suggestion to SQLite, not reserved memory, a hard RSS limit or a bound on all database/process memory. WAL, statements, temporary databases and other allocations are separate. An eight-connection 256 MiB plan yields 32768 KiB per connection; fewer live connections do not receive the unused share.

A full shared-manager/process restart applies a changed saved target. Opening another Store on the same live manager cannot apply a different target. If that manager's pool maximum is explicitly reconfigured, the per-connection share is recalculated from its originally applied aggregate, not from a newly saved restart-only value. Replacement pools, failed-open restoration and conversion cutover retain the applied foreground options. Configuration is attached to physical connection creation; ordinary mail requests do not run cache PRAGMAs or sample counters.

When custom tuning is enabled, private background maintenance, cached-body expiry, change-history retention and online conversion copy/cleanup connections use an explicit small 2000 KiB MAIN target each. They are **excluded from the foreground aggregate**. Their count and other memory still matter for process sizing. With `null`, auxiliary behavior is unchanged. The conversion target's eventual serving pool uses the foreground options, not the temporary copy connection's small target.

## Observability

The database panel reports the applied per-connection target, planned foreground aggregate, separate auxiliary target, and `PRAGMA cache_size` measured on one connection by the existing storage inspection. A bounded idle-only sweep samples real `sqlite3_db_status` counters from owned foreground handles: cache bytes, hits, misses, writes and spills. It does not create connections, wait for busy request leases or execute SQL. Up to 32 handles are sampled with a cooperative 25 ms deadline; synchronous status calls and operating-system scheduling are not preempted by that deadline. Held leases prevent duplicate counting within the sweep; incomplete coverage is explicit. Failed/unavailable counters remain unknown, never fabricated zero.

The small `mw-sqlite-status` crate confines the five read-only FFI operations to an actual SQLx handle lock, uses `resetFlag=0`, and exports no raw pointer, operation selector, SQL or key. Store retains its `forbid(unsafe_code)` rule. Per-open opaque connection epochs distinguish replacement handles; cache counters are SQLite signed 32-bit cumulative values and can wrap/reset. Negative counters are unknown; no rates are inferred across samples or generation changes. Cache counters cover all attached pagers on each sampled handle, while the configured target applies to MAIN only. Shared-cache configurations can count shared pages more than once. Cache events are not physical disk I/O. Sampled bytes describe only sampled handles, not total server memory or a hard aggregate bound.

## Verification and controlled comparison

Source-authored tests cover null option preservation, bounds/rounding, no diagnostic SQL, idle sampling without pool growth, real cache misses/writes, keyed reopen, changed maximum with a pending saved target, small auxiliary scope and a genuine NONE-to-INCREMENTAL conversion cutover. UI tests distinguish the planned target from partial measured usage and unknown counters. These require execution before any runtime claim.

Future capacity comparison must use one immutable release revision containing this option, identical policies, sealed storage, dataset, pool ceiling, application/generator resources, telemetry and positive publication checks. Compare `null` with 256 MiB explicitly, retain effective PRAGMA and coverage evidence, and report actual resource use alongside throughput. This option alone establishes no throughput improvement and does not change the default. Supporting 10,000 users or 40,000 requests/second remains unproven.

## Explicit fixture cache experiment witness

For a future same-code comparison, set the native application fixture and controller option `MW_LOAD_FIXTURE_SQLITE_CACHE_EXPECT=null` or a canonical integer `16` through `1024`. This option **does not configure** the cache: configure `MW_DB_POOL`/the saved startup policy separately. The private handoff and controller expectation must agree; proxy/PostgreSQL fixtures reject this experiment. Absent expectation leaves baseline controls and qualification unchanged.

`mw-store/sqlite-cache-diagnostics` is enabled only by the existing server `load-test-fixtures` feature. The additive audit API is not called by normal application routes. In the opted-in native fixture, the existing token-protected diagnostic boundary calls it before and after measured work. It pins the current serving generation, holds distinct idle pool leases, and combines actual `PRAGMA cache_size` reads with the fixed read-only handle counters. It never opens a new connection, waits for a busy lease, emits filenames/keys or changes an authority decision. The maximum is 32 handles and a cooperative 25 ms deadline; queued SQLite work and operating-system scheduling are not preempted. Lease ownership is local and drops on error/cancellation.

The strict report sanitizer whitelists finite numeric/boolean fields. A cache experiment cannot qualify from configuration alone: every stage boundary requires a nonempty complete sample of all **currently open** serving handles, coherent maximum/target metadata, distinct known epochs and known counters. A custom target requires each actual negative `cache_size` to equal the planned share. This proves neither that the maximum number of connections was open nor a hard memory limit. Busy/partial/timeout/missing or inconsistent proof rejects the experiment. Null captures effective driver/header values without assuming `-2000`. Counter reads include attached pagers, and their own audit PRAGMA work can add cache events; no physical-I/O or throughput inference is made from them.

The helper is included in fixture overlays. Legacy absent witness fields remain optional, but opting into a cache experiment against an old image without this capability fails closed. The ordinary publication/security/telemetry/workload qualification gates remain mandatory and unchanged.
